# #7132: pre-merge compile check in merge-pr

Growth: about +146 non-test lines and +0 files in `cmd/goobers`, all in
`mergepr.go`. The check itself (fetch the base tip and pinned head, merge them
in a disposable worktree, run the commands, classify the outcome, clean up)
lives in the new `internal/premergecheck` package.

## Why the growth belongs in the command package

- **`runPreMergeCheck`** builds the request from merge-pr's own state: the
  locked poll, the pinned head, and the workspace origin. It also injects a git
  runner built from cmd-local helpers (`hardenedWorkspaceGitArgs`,
  `composeGitEnv`) so the check's git calls behave like every other stage git
  call against the shared mirror.
- **`preMergeCheckGitAuth`** reuses the landing credential the stage already
  holds, and fetches GitHub/Gitea heads through `refs/pull/<n>/head` so fork
  heads resolve; head movement maps to the existing stale-verdict reason. It goes through `providerToken`, `gitAuthEnvFor` and
  `stageADOCredentialSource`, which are cmd-local. `providerToken` must take a
  constant capability so the provider-capability manifest test can see it.
- **`preMergeCheckReason`** renders the outcome as one of merge-pr's stable
  refusal tokens (`merge-conflict`, `pre-merge-check-failed`), which
  record-merge-refusal routes on.
- **`preMergeCheckEnv`** strips goobers-delivered credentials from the
  environment the untrusted PR code builds under.
- **`liveConjunctReasons`** is a pure move of existing code out of
  `runMergePR`, kept so the function's complexity and body length don't grow.
  Its net growth is the function signature only.
- The wiring in `runMergePR` (input parse, call, fail-closed exit) and the help
  text make up the rest.

## Could any of it live elsewhere?

`preMergeCheckEnv` could move into `internal/premergecheck` if a second caller
appears. The auth plumbing could follow once the stage git-auth helpers are
extracted from `cmd/goobers` (the broader extraction work). Neither move is
worth it for one caller today.
