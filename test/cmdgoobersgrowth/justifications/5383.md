# #5383: settle cleanup targets whose checkout is already gone

Growth: +11 non-test lines and +0 files in `cmd/goobers`.

## Why the growth belongs in the command package

- **Three call sites** (`recoverycleanup.go` current and historical targets,
  `recoveryworkerremote.go` worker target). Each recovery cleanup guard is
  wired here, so each needs one call to `recovery.SettleGoneCleanupTarget`
  before it reads the checkout, plus the early return when the target was
  settled.

## Could any of it live elsewhere?

The logic itself already lives outside the command package: the gone-target
handling is `internal/recovery/gonetarget.go` and the shared-repository
lookup is `worktree.Manager.LinkedWorktreeRepository`. Only the call sites
remain, and they cannot move until the recovery guards themselves leave
`cmd/goobers`.
