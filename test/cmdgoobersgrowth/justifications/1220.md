# #1220: TUT-A8 configrepo:write and the config-repo target

Growth: about +530 non-test lines and +2 files in `cmd/goobers`
(`configrepotarget.go`, `configcheckout.go`).

## Why the growth belongs in the command package

- **`configcheckout.go`** is the new `goobers config-checkout` stage command: a
  `stageCommand` handler, its help text and one git clone/checkout helper. Stage
  commands are registered in `runtime_capabilities.go` and read the stage
  environment (`GOOBERS_CRED_*`, `GOOBERS_INPUT_*`, run context), so the handler
  itself cannot live outside this package.
- **`configrepotarget.go`** resolves the config repository from the instance's
  `workflowSource` (or the pod-side `configRepo` inputs), reads the
  `configrepo:write` credential and verifies a checkout's origin. It is the
  stage-environment glue shared by `push-branch`, `open-pr` and
  `config-checkout`.
- **`runnerwiring_credentials.go`** gains the composition-root wiring for the
  write-scoped installation-token source (the sibling of the existing
  `newWorkflowSourceAppTokenSource`). It must sit beside that function: only
  `cmd/goobers` may import `internal/githubapp` together with
  `internal/instance`.
- **`push-branch` / `open-pr`** gain a `--config-repo` flag and the small
  target-selection seam (`openPRTarget`, the base-branch parameter on the empty
  branch check). These are edits to existing stage handlers.

## Could any of it live elsewhere?

`parseConfigRepoURL` and `configRepoTarget` are pure and could move to
`internal/instance` next to `WorkflowSource` once a second consumer (for example
the daemon-side preflight for the capability) needs them. Nothing else outside
`cmd/goobers` consumes them today, so they stay with their only callers.
