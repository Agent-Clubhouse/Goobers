# #5895: refuse unknown workflows before accepting a daemon trigger

Growth: about +45 non-test lines and +0 files in `cmd/goobers`.

- `writeplanes.go` (+40). `daemonTriggerService` gains a startup catalog and
  `validateTriggerTarget`. It picks the catalog the daemon's trigger plane
  should check: the attached scheduler's reload-aware set, or the startup
  entries before the scheduler attaches. It maps the result onto the plane's
  existing `workflow_not_found` / `workflow_ambiguous` API refusals. Pod
  principals that name an unconfigured gaggle are not shown other gaggles'
  workflows.
- `triggeracceptance.go` (+6 net). The durable trigger service passes that
  check to the queue as its admission callback and returns the typed refusal.
- `up.go` (+0 net). Wires the startup catalog onto the existing builder chain.

## Could any of it live elsewhere?

The reusable parts are already outside this package. Resolution and the
user-facing message (`ResolveWorkflowTarget`, `UnknownWorkflowError`,
`WorkflowIdentities`, `EntryIdentities`) are in `internal/localscheduler`.
The "check only for new keys, so redelivery still replays" rule is
`triggerqueue.Store.AcceptAdmitted`. What stays here is how the daemon's
trigger plane is wired (scheduler attachment, startup entries, pod scoping,
HTTP refusal codes). That state only exists on `daemonTriggerService`.
