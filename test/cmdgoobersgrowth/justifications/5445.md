# #5445: pinned rebuilds reuse the run's admitted config generation

Growth: about +15 non-test lines and no new files in `cmd/goobers`
(`configgeneration.go`, `daemon.go`).

## Why the growth belongs in the command package

- **`schedulerExecutionGeneration`** (`configgeneration.go`) chooses between the
  run's admitted generation and a fresh retained capture before
  `buildSchedulerDefinitions` compiles runners. Recovery and intervention
  rebuild a run's runtime from its retained tree; re-capturing that tree is not
  byte-stable on Windows, so the rebuilt runner got a new generation identity
  and every later CLI stage failed `config_generation_mismatch`.
- **`schedulerDefinitionsInput.PinnedGeneration`** and the generation argument
  on `generationDefinitionBuilder` carry that identity through the existing
  composition-root builder. Both types and every caller already live in
  `cmd/goobers`.

## Could any of it live elsewhere?

No. The scheduler-definition composition root, the generation resolver and the
child runtime builder are all `cmd/goobers` wiring; the change threads one value
through them rather than adding new behaviour.
