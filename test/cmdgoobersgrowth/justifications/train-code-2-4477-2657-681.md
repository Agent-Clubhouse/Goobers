## Why the growth belongs in the command package

- **`issueCloseOutIdempotencyKey`** (`cmd/goobers/issuecloseout.go`, +12 lines,
  most of them doc comment). This is the `issue-close-out` stage's own policy for
  naming its single close-out update: `issue-close-out/<run>/<item>/<status>`.
  - It uses the subcommand name, not `GOOBERS_STAGE`, whose spelling differs
    by substrate (#4119).
  - It includes the status, so a park update and a done update from the same
    run never adopt each other's comment.
  - The key-agnostic mechanism (the marker, the adopt-on-retry logic and
    `PartialUpdateError`) lives in `providers` (`rest_compound_update.go`).
    Only the stage-specific naming is here.
- **Passing the key to the two existing update calls** (+2 net lines). These
  are the stage's own `UpdateWorkItem` and `UpdateWorkItemStatus` requests.
- **The `linkedImplementationPullIDs` doc comment** (`cmd/goobers/backlogquery.go`,
  +1 net line, comment only). This function reads the close-out comments the
  stage above writes. The comment now says those comments also carry the
  operation marker. No code changes here, because `providers.StripAttribution`
  removes the marker together with the attribution footer.

## Could any of it live elsewhere?

Two pieces could reasonably move out of `cmd/goobers`:

- **The key helper.** If more stages start keying their updates,
  `providers` (or a small stage-keys package) could expose a single
  `OperationKey(stage, run, item, discriminator)` builder, leaving each stage
  with a one-line call.
- **The close-out comment format.** `linkedImplementationPullIDs` and the
  comment prefix and suffix could move into a small close-out package shared
  by the writer and the reader.

Neither move is worth it for one caller today. Both would be follow-ups to the
broader `cmd/goobers` extraction work, not part of this train.
