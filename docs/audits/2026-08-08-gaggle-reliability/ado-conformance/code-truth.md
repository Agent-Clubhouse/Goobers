## 2. PR LABELS

ADO PRs do support labels (`.../pullrequests/{id}/labels`) — **our code never writes them, only reads**: list mapping `providers/ado_pullrequests.go:393-396,412`; `PollMergeQueueEntry` labels `providers/ado_landing.go:182-185`. Wire: PR 359 has `labels: None`.

Critical asymmetry: ADO `PollPullRequest` populates **neither `Labels` nor `CommentsSince` nor `MergeableState`** (`ado_pullrequests.go:154-170`), so merge-pr's opt-out conjuncts (`goobers:no-merge-review` `cmd/goobers/prselect.go:34`, `goobers:run-aborted` `cmd/goobers/runabortlabel.go:32`; checks at `cmd/goobers/mergepr.go:199-210`) and `pinnedPassVerdict` (`mergepr.go:407-424`) would silently see nothing.

Per-flow disposition on ADO: `needs-remediation`/`blocked-on-sibling`/verdict labels are applied via `provider.UpdateWorkItem(PR number)` on GitHub (PR-as-issue, `cmd/goobers/applyverdict.go:789-799`) — that path is GitHub-gated (`applyverdict.go:589-608`), which is the only thing preventing a **wrong-object hazard**: on ADO `UpdateWorkItem` addresses `_apis/wit/workitems/{id}`, so a PR number would mutate an unrelated work item with that ID. Verdict: gap (safe today only by GitHub-gating; wiring ADO must not reuse the PR-as-issue trick).

## Requirements for a working ADO merge-review workflow

**What works on ADO today** (wire-proven last night + this audit): the implementation loop — backlog-query claim (WIQL/ledger/breadcrumb) → gather-implement-context → open-pr (idempotent find-or-create, 4000-char body cap) → report-pr-status (native PR status) → ci-poll (branch-policy evaluations) → issue-close-out status=in-review + park paths. **No stage of merge-review's chain runs on ADO** — pr-select, gather-pr-context, apply-verdict (non-moot), merge-pr, merge-queue-poll, post-merge are all GitHub-hardwired — even though every provider-side landing primitive they need is implemented and declared.

To make merge-review work on ADO:

1. **Stage dispatch + capability plumbing**: per-provider switches in `mergepr.go`, `prselect.go`, `gatherprcontext.go`, `mergequeuepoll.go`, `postmerge.go`, `prremediationlifecycle.go` mirroring `issuecloseout.go:242-276`, resolving via `adoauth.Provider` (`adoprovider.go:51-61`, `internal/adoauth/source.go:21-49`: pat/azure-cli/workload/managed) instead of the literal `github:pr:merge`/`github:pr:write` env grants (`internal/capability/capability.go:60,76`).
2. **Verdict transport** (pick one; (c) is the ruled/working alternative): (a) implement `pr.review.submit` as an ADO reviewer vote — requires an authenticated-identity GUID (connectionData) and, unlike GitHub #870, ADO permits voting on your own PR; (b) PR-thread comment handoff + `pr.review.threads`; (c) `report-pr-status` publishes the verdict as PR status `goobers/validation` and a **status-check branch policy** gates it — then merge-pr's verdict conjunct reads policy evaluations instead of the sticky comment. Regardless, pr-remediation's finding-history needs an ADO comment surface (threads) or must be disabled.
3. **AuthenticatedLogin equivalent** for ADO (connectionData) — prerequisite for trusted-comment filtering AND closes the claim-spoof gap.
4. **merge-pr semantics on ADO**: `DetectMergePolicy` (any blocking scoped policy → MergeQueue) routes to `EnqueuePullRequest` (arm auto-complete; ADO's completion job is the queue) with `PollMergeQueueEntry` as the sole landed-oracle; Direct → `MergePullRequest` (SHA-pinned, async-job-awaited; `mergeCommitMessage` only honored for squash/noFF).
