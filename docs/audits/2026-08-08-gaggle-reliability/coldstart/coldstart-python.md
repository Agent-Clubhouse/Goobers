completed=True validate_clean=True tweaks=10 (validate 1, runtime 9), yaml_authored=186

## Summary
I got to a `goobers validate --strict --check-harness --check-repos` clean instance implementing backlog-curation + implementation against the Python testbed, and honestly the shipped material carried most of the weight: `goobers examples show` handed me both workflows nearly production-ready with rationale comments on almost every field, and docs/guides/arbitrary-repo-onboarding.md is written for precisely this task. First validate after my first honest attempt was already green except for four SKILL002 warnings. The real story is what validate could not tell me: it stayed silent while my config referenced seven GitHub labels of which zero existed, while `connect --seed` created only two of them, while three goober instruction files still told the agent it worked on 'the Acme Web gaggle' and to avoid running `npm run ci` on a Python repo, and — worst — while the local-CI command would have run pytest under Python 3.9.6 against a package declaring requires-python >=3.12, because under `sh -lc` the daemon's login-shell PATH resolves `python3` to the system interpreter rather than any version-manager shim. Nine of my ten tweaks were found by reading docs, probing the shell myself, or parsing a --json envelope; exactly one was caught by validate up front. The recurring pattern is that the prose documentation already knows about most of these traps (the default `goobers` label, the label bootstrap, the too-hot budgets) but the tooling does not enforce or check any of them, so validate-clean is a much weaker signal than a first-hour user would reasonably assume. The one genuinely undocumented thing, `spec.skills`, I solved by guessing the package layout from the shipped agent toolkit — and then discovered an empty directory satisfies the check anyway.

### 4. [docs-gap / via validate]
4. Authored four skill package directories (triage, implement, run-tests, review) under config/gaggles/ledger/skills/ to clear SKILL002.
- expected: The skill names used by every shipped example (`triage`, `implement`, `run-tests`, `review`) resolve to something the product ships.
- actual: 4x `WARNING SKILL002 gaggles/ledger/goobers/curator/goober.yaml Goober/curator: spec.skills declares "triage", but no skill package directory was found at "gaggles/ledger/skills/triage" or "skills/triage"`. Under --strict these become errors (exit 1). Nothing anywhere documents the skill-package format: `goobers explain --human Goober.spec.skills` says only 'Named skills available to this goober'; docs/requirements/goober.md mentions skills in a one-line table row; the goobers-dsl-author DSL reference mentions `skills` once inside a list with no explanation; no guide covers it. I guessed the format from the shipped agent-toolkit layout (a directory with SKILL.md + name/description frontmatter) and it cleared the warning. Separately: an EMPTY directory also clears it — the check is existence-only, so --strict gating on SKILL002 can be satisfied with `mkdir`.

### 5. [default-assumption / via guessing]
5. Rewrote ciCommand from the reference `["python3","-m","pytest","-q"]` to chain an editable install first, via `sh -lc`.
- expected: The shipped python-service reference gaggle's `ciCommand: ["python3", "-m", "pytest", "-q"]` would be the right local-CI command for a normal Python repo.
- actual: ledgerlite is a src-layout package (`package-dir = {"" = "src"}`) with tests that do `from ledgerlite.models import Transaction`. Bare pytest cannot import it — it needs `pip install -e '.[dev]'` first, which is exactly what the repo's own .github/workflows/ci.yml does. Because `ciCommand` is argv rather than a shell line, chaining the two steps requires wrapping in `sh -lc` yourself. `validate` never inspects the repo, so nothing flagged that the reference command would fail on the very stack it is the reference for.

### 6. [invariant-assumption / via guessing]
6. Changed both interpreter invocations in ciCommand from `python3` to `python3.12`, and documented the host prerequisite in instance.yaml.
- expected: With `requiredCapabilities: [python@3.12]` declared and `runner.capabilities: [python@3.12]` advertised, `python3` inside the local-ci stage would be a 3.12 interpreter.
- actual: I probed the resolution myself. In my interactive shell `python3` = 3.11.9 (pyenv shim). In the scratchpad worktree the SAME shim path resolves to 3.9.6 (pyenv picks by cwd `.python-version`). Under `sh -lc` — which is literally how ciCommand runs — `python3` = /usr/bin/python3 = Python 3.9.6, because a login shell has no shim dir on PATH. pyproject.toml declares `requires-python = ">=3.12"`, so this would have failed at pip-install time with a packaging error rather than a version error. `goobers validate --strict --check-harness --check-repos` was completely clean throughout. quickstart.md §'Prerequisites' documents exactly this hazard class for Go (golangci-lint must be on the *daemon's* PATH; the GOPATH/GOCACHE/GOFLAGS family is passed through into every stage) but there is no Python or general-stack equivalent, and no way to ask the tool what a stage's PATH will actually resolve to.

7. Hand-created 5 more GitHub labels after `connect --seed` created only 2.

Nothing in validate checks label existence, and `doctor --repo` returned 'REPO POLICY: no repo declares a policy manifest; nothing to check'.

## Delights
- `goobers init` runs a full validation pass on its own output and ends with a literal 'Next: edit these files before running a live workflow:' list naming the two files. I never had to ask what to do next.
- Nearly every command ends with a `next:` line, and the chain is genuinely correct: init -> edit files, scaffold -> validate, connect -> `goobers run backlog-curation`. The second connect run even updated its suggestion from `default-implement` to `backlog-curation` because it re-read my actual workflows.
- `goobers examples list` returned exactly `backlog-curation` and `implementation` — precisely the pattern I was asked to build — and `examples show` emits ~600 lines of near-production YAML where almost every field carries a comment explaining *why*, including the tradeoffs (e.g. why park-escalated exists instead of routing straight to `@escalate`). This is the single biggest reason the exercise succeeded.
- `goobers explain --human Goober.spec.capabilities` printed the complete enum of 20 allowed capability values. That turned a guess into a lookup, and is how I confirmed `agent:model` was a real capability name.
- `goobers connect` preserved every YAML comment in the files it rewrote, and on the second invocation correctly found my *renamed* `ledger` gaggle and reported already-connected files as `skipped` instead of clobbering them.
- `connect --json` returns a versioned envelope with explicit `created`/`skipped`/`path`/`nextCommand`. That machine-readable created-list is exactly how I caught the label under-seeding — an opaque 'done' would have hidden it.
- `goobers workflow show implementation` renders the whole DAG including every gate's per-branch target (pass/fail/needs-changes/escalate/timeout). After editing copied YAML this was an instant confirmation that I hadn't severed an escalation path.
- docs/guides/arbitrary-repo-onboarding.md reads like it was written for exactly this task: a foreign repo through one curation run and one implementation PR. It hands you the least-privilege token permission table, the exact placeholder grep, a copy-pasteable idempotent label bootstrap, and the expected behaviour of each run so you can tell success from silent no-work.
- Failures degraded gracefully instead of blocking authoring: GitHub rate limiting during `connect` and `--check-repos` surfaced as named warnings ('could not determine repository size: github rate limited') while the actual work still completed with exit 0.
- `validate --check-harness` printed `HARNESS copilot: OK` with no setup on my part, and `goobers versions` proactively reported 'this host: darwin/arm64 (go1.26.5) — supported'.
- Diagnostics carry stable codes, the offending file path, and the exact search paths tried — SKILL002 listed *both* candidate directories it looked in, which is the only reason I could guess the skill-package layout at all.

## Docs notes
The narrative docs are unusually good and are the reason this worked: quickstart.md and arbitrary-repo-onboarding.md form a real ladder, the second one targets my exact task, and config-examples/README.md's 'Copying subsets safely' section correctly told me which files travel together (gaggle + both goobers + workflow). Where docs fail, they fail in a specific pattern: prose knows about a trap that the tooling does not enforce. The `goobers` default backlog label, the label taxonomy that must pre-exist, and the too-hot default budgets are all documented warnings that `validate` is silent about. Concrete gaps found: (1) `spec.skills` is completely undocumented — no guide, no cookbook, and `explain` returns a tautology — yet every shipped example uses it and --strict fails on it; I authored skill packages purely by pattern-matching the agent-toolkit layout. (2) `agent:model` is required per the scaffolder's own comment and per the onboarding guide, but absent from all 12 shipped example goobers. (3) config-examples/ is documented as 'a checked-in config source' and its README tells you to run `goobers validate --source-tree <path>` on it, but running that against config-examples itself fails with `error: .../config-examples/instance.yaml.example not found (not a config source tree)` — the reference layout diagram in that README omits the `instance.yaml.example` that arbitrary-repo-onboarding.md §3 shows and that --source-tree requires. (4) quickstart's excellent daemon-PATH warning is Go-only; there is no equivalent for Python/Node/Java despite four polyglot reference gaggles shipping.

## DSL ceremony notes
The DSL itself was rarely the problem — I wrote almost no novel YAML structure, because `examples show` gave me both workflows nearly complete and my edits were 2 gaggle names, one readiness field, one command, and two prose strings. The ceremony is concentrated in three places. First, there is no non-interactive route to the standard curation+implementation pair: `init --guided` can select both, but only through prompts, so a scripted setup must delete the scaffolded `coder`/`default-implement`, hand-create three goober directories, and copy two 200-400 line workflows. A `--template=standard` or `init --workflows=backlog-curation,implementation` would erase most of this exercise. Second, `ciCommand` being argv rather than a shell line means any real project whose local CI is 'install, then test' (which is most non-Go stacks, including the repo's own GitHub Actions job) must hand-roll `sh -lc "... && ..."`; the shipped python/java/dotnet reference ciCommands are all single-step and would not survive contact with a src-layout package. Third, the `local-ci` task carries a `command:` that the gaggle's `ciCommand` silently overrides — so the workflow file contains a stack-specific command that is dead when the gaggle sets one, and stale-but-live when it does not. I kept the two identical deliberately, but a smart default (inherit the gaggle's ciCommand, or make the task command optional) would remove a real footgun. Positively: gates read very well — one evaluator each, every branch named, no silent pass — and `workflow show` makes the resulting state machine auditable, so the ceremony that does exist is at least legible.
