# Run provenance stops at workflow/goober digest — the binary that ran, and every scheduler lifecycle event around it, are invisible to telemetry

Suggested labels: `area:telemetry`, `area:runner`, `type:bug`, `sprint:v1-breadth`

## Problem

`run.yaml` pins exactly what a run started on for its workflow and goober content — but not which daemon binary executed it. Answering "which fix was live for this run" requires manually time-joining a run's `startedAt` against the scheduler's own `events.jsonl` for `daemon.started` records, by hand, per run — there is no query surface for it.

That manual join is also the *only* way to answer it, because the telemetry ingest never stores the daemon lifecycle events it would need: `daemon.started`, `daemon.clean_shutdown`, `daemon.dirty_restart`, and `config.reloaded` are all real, already-journaled event types that the rollup ingest's event-type switch silently drops. A daemon that crashed, restarted onto a stale binary, or ran for days on an uncommitted config change leaves no trace in `scheduler_events` — only in a raw journal file an operator has to grep by hand. And `scheduler_events` itself has no `gaggle` column, so even the events it does ingest cannot be attributed to one gaggle in a multi-gaggle instance without a second join back to `runs`.

Net effect: the single highest-leverage reliability fact this system could show an operator — "which binary, on which config, made this decision" — is the one fact its own telemetry cannot produce a query for.

## Evidence

- `internal/journal/identity.go:46-76` (`RunIdentity`) — fields present: `Workflow`, `WorkflowVersion`, `WorkflowDigest`, `GooberDigest`, `Gaggle`, `RunControls`, `Trigger`, `Inputs`, `StartedAt`. No binary/build-version field of any kind.
- `internal/telemetry/rollup/ingest.go:807-808` (`ingestSchedulerLog`'s event-type switch): admits only `eventInitCompleted, eventTriggerFired, eventTickSkipped, eventProviderQuotaReset, eventPollShed, eventClaimAcquired, eventClaimReleased, eventClaimForceReleased, eventRunStarted, eventRunFinished, eventError` (plus `eventWorkflowStarved` in a second case at line 831). No `case` for daemon lifecycle or config-reload events — they fall through unhandled, silently, every ingest cycle.
- `internal/journal/event.go:132,138,141,144` — `EventConfigReloaded`, `EventDaemonStarted`, `EventDaemonCleanShutdown`, `EventDaemonDirtyRestart` are real, defined event types the scheduler already journals (confirmed live: 59 `daemon.*` events observed in one 15-day window per the daemon-stability audit below) — the gap is entirely on the ingest side, not the producer side.
- `internal/telemetry/rollup/schema.go:129-137` — `scheduler_events` columns: `seq, type, workflow, run_id, reason, status, occurred_at`. No `gaggle` column, though every raw journal event already carries one.
- `docs/audits/2026-08-08-gaggle-reliability/domains/audit-deployment.md`, finding `per-run-binary-provenance-gap` (LOW/confirmed): "run.yaml records workflowDigest/gooberDigest/workflowVersion but NOT the daemon binary version, and telemetry.db's scheduler_events ingests no daemon lifecycle events ... so attributing a given run to a binary requires a time-join against journal daemon.started events."
- `docs/audits/2026-08-08-gaggle-reliability/domains/audit-daemon-stability.md`, finding `telemetry-observability-gap` (MEDIUM/confirmed): "the telemetry ingest whitelist silently drops every daemon-instability signal: daemon.started/clean_shutdown/dirty_restart, config.reloaded, claim_lock_slow, claims_lock_timeout, and runner.annotation never reach scheduler_events/scheduler_errors, and scheduler_events has no gaggle column so quota skips cannot be attributed per gaggle in SQL." Same audit records the practical cost: 29 daemon sessions in 15 days, 45% dirty stops, five `-dirty` (uncommitted) builds run in production, all invisible in `scheduler_events` today and reconstructable only by grepping the raw journal.
- Same audit, deployment domain: the K1 finding in this audit's own top-level README was initially wrong ("fix never ran") specifically *because* binary provenance required manual journal archaeology to get right the first time — a live demonstration of the cost this gap imposes even on a dedicated forensic pass.

## Proposed direction

Two independent, additive changes, both schema-compatible with existing consumers:

1. **Stamp the binary into `run.yaml`.** Add a `runnerVersion` (or equivalent) field to `RunIdentity`, populated the same way `WorkflowDigest`/`GooberDigest` already are at run `Create` — from build info already available to the running binary (the same version string `goobers version` and `up.lock` already report). This is the same precedent as `GooberDigest` (`TUT-P1`, closed): a content-identity field folded into `run.yaml` once, at creation, never edited. Optional/omitted for runs predating the field, exactly like `WorkflowDigest` already handles pre-digest runs.
2. **Widen the scheduler-event ingest switch and add a `gaggle` column.** Add `eventDaemonStarted, eventDaemonCleanShutdown, eventDaemonDirtyRestart, eventConfigReloaded` as ingested cases in `ingestSchedulerLog`, storing the binary version (already present in the `daemon.started` payload) and old/new config digest (already present in `config.reloaded`, per `internal/localscheduler/scheduler_test.go:329`) in the existing `runner_json`-style free-form column other rows already use for event-specific detail — no new table needed, matching how `stage_attempts`/`provider_mutations` already stash runner-local detail. Add `gaggle` to `scheduler_events` (nullable, populated from the journal event's own `gaggle` field where present — daemon-level events like `daemon.started` have none, per-gaggle events like `trigger.fired`/`tick.skipped` do), so a multi-gaggle instance's per-gaggle quota/scheduling picture doesn't require a second join back to `runs` for events that never had a `run_id` to join through in the first place.

Zero-config result: every daemon build already stamps its own version at compile time and the scheduler already journals every lifecycle event listed above — this proposal changes what the *rollup ingest* keeps, not what any operator has to configure or any workflow author has to declare.

Explicitly not proposed here: `claim_lock_slow`/`claims_lock_timeout`/`runner.annotation` ingestion (cited in the daemon-stability finding as suffering the identical drop) — those are lock-contention and per-stage annotation events with a different consumer shape (they'd land in `stage_attempts`/`run_errors`, not `scheduler_events`) and are a distinct, separately-sized fix sharing only the root cause (the same switch statement), not the same schema target.

## Alternatives considered

- **Reconstruct binary provenance purely from the journal at query time** (skip the `run.yaml` field, teach the portal/CLI to do the time-join against `daemon.started` on demand) — rejected: this is exactly the manual process that produced this audit's own initial false finding (K1), it requires the scheduler journal to still be retained and reachable at query time (not guaranteed after compaction/pruning), and it can't be pinned/immutable the way `run.yaml`'s other identity fields are — a run's provenance should be fixed at `Create`, not re-derived from a mutable external log every time someone asks.
- **A general-purpose "ingest everything" mode instead of widening a specific switch** — rejected: the switch is a deliberate whitelist (the ingest code comment notes bounding per-tick work to genuinely new events); an unbounded ingest of every event type reintroduces exactly the unbounded-growth failure class this audit's daemon-stability findings already flag elsewhere (the 281MB error-blob incident, the uncursored span re-ingest). Naming the specific four event types keeps the addition bounded and reviewable.

## Size and risk

**S–M.** Change 1 (binary version in `run.yaml`) is S: one field, populated once at `Create` from data the binary already has about itself, optional for legacy runs — no migration, no schema break, same pattern as an already-shipped precedent. Change 2 (ingest whitelist + `gaggle` column) is S–M: one `ALTER TABLE ADD COLUMN` (additive, nullable — safe under the existing `CREATE TABLE IF NOT EXISTS` migration style already used for this table's evolution), four new `case` arms reusing the existing insert statement shape, no change to any already-ingested event's row shape. Both changes are purely additive to schema and ingest — no consumer of `scheduler_events` or `run.yaml` today reads a field this proposal removes or repurposes, so no downstream break.
