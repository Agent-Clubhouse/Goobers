# Three `ado:*` capability enum values are dead, one is preview-only, and provider-dispatched backlog/PR-status built-ins require GitHub-spelled capabilities on every provider

Suggested labels: `area:contracts`, `area:providers`, `type:bug`, `goobers:needs-human`

## Problem

A workflow author configuring an Azure DevOps-backed gaggle cannot correctly guess which capability string a backlog-touching or PR-status stage requires. `goobers explain goober.spec.capabilities` prints five `ado:*` grants (`ado:code:read`, `ado:pr:comment`, `ado:pr:write`, `ado:pr:status`, `ado:work-items:write`) that read as the ADO-native vocabulary, but every shipped backlog built-in (`backlog-query`, `backlog-health`, `backlog-dedupe`, `issue-close-out`, and siblings) demands the literal GitHub-spelled `github:issues:write`/`github:issues:read` regardless of the gaggle's configured provider, and `report-pr-status` — the one stage whose own man page calls itself "Azure DevOps PR status" — rejects `ado:pr:status` outright and requires `github:pr:write`, with an error that enumerates GitHub and Gitea and never mentions ADO. An author who declares the seemingly-correct `ado:work-items:write` or `ado:pr:status` gets no compiler help finding the actual required string; the grant is either silently inert or a hard validation failure, and the fix has to be reverse-engineered from validator error text one stage at a time.

## Evidence

- `internal/capability/capability.go:88-104` — the five `ado:*` constants and their doc comments (`ADOCodeRead`, `ADOPRComment`, `ADOPRWrite`, `ADOPRStatus`, `ADOWorkItemsWrite`), all listed in `All()` at `capability.go:135` and therefore `Known()`/schema-valid.
- Of those five, verified today (2026-08-08, `grep -rn "capability\.<Name>" --include="*.go" .`, excluding the declaration file itself):
  - `ADOCodeRead`, `ADOPRComment`, `ADOWorkItemsWrite` — **zero references anywhere**, including tests. Wholly dead code paths in the DSL surface.
  - `ADOPRWrite` — referenced only in the provider-neutral/provider-specific mutual-exclusion guard (`internal/workflow/v_current/compile.go:406-409`, mirrored in `v_next/compile.go:419-422`: `capabilities[string(capability.ProviderPRWrite)] && (capabilities[string(capability.GitHubPRWrite)] || capabilities[string(capability.ADOPRWrite)])`). It can trigger a *rejection* if declared alongside `provider:pr:write`, but no built-in's manifest ever accepts it as satisfying a requirement — it cannot be used to unlock anything.
  - `ADOPRStatus` — required by exactly one policy action, and only in the **preview, not-yet-adopted** DSL 2.0 interpreter: `internal/workflow/v_next/policy_actions.go:48-54` (`"report-pr-status": {requiredCapabilities: []capability.Capability{capability.ADOPRStatus}}`, referencing issue #772). `internal/supportmatrix/supportmatrix.go:44,47` — `CurrentDSLVersion = "1.4"`, `NextDSLVersion = "2.0"` at `LevelPreview`. Every load-bearing shipped workflow (merge-review, implementation, pr-remediation, backlog-curation, work-nomination) still pins 1.4 — measured in epic #2695 (below) at roughly 1:10 adoption for 2.0. `v_current`'s parallel file, `internal/providerstage/manifest.go:199-204`, still requires only `capability.GitHubPRWrite` for `report-pr-status`, with the comment "the GitHub PR-write grant also authorizes the Gitea commit-status path" — ADO is not in the sentence.
- `internal/providerstage/manifest.go` — the compile-time manifest every `v_current` (1.4) stage validates against. Every backlog-touching entry requires the GitHub-spelled capability unconditionally: `backlog-dedupe` (line 66), `backlog-assignment` (72), `backlog-health` (78), `backlog-query` read/write split (84-85), `pr-select`-adjacent lookups (92, 98), remediation-issue routing (123, 130, 137), `issue-close-out` (156), merge-queue-poll eviction (170), post-merge issue updates (184), remediation label cleanup (210), rebase outcome routing (217), late-merge reconciliation (225), finding responses (239), behind-base routing (252) — all `capability.GitHubIssuesWrite`/`GitHubIssuesRead`, none accept an ADO-spelled alternative.
- `docs/adr/0002-provider-neutral-capability-namespaces.md` — the accepted decision (2026-07-28, issue #1810) this proposal must stay consistent with: "A stage that selects the implementation from the invocation's configured repository provider uses `provider:<resource>:<verb>`" (line 27-29); a genuinely provider-specific operation keeps a distinguishing name, citing "Azure DevOps PR status publication" by name as the worked example (lines 18-20); migration is fail-closed — "a stale provider-specific declaration fails validation... the compiler does not silently rewrite it" (lines 49-51).
- `docs/audits/2026-08-08-gaggle-reliability/coldstart/coldstart-ado.md` — TWEAK 1 (24 validation errors from declaring `ado:work-items:write` on an ADO backlog; fix was substituting the literal `github:issues:write` string, which then routed correctly to an ADO credential at runtime — confirming these built-ins already dispatch through the configured provider at the credential-injection layer, just not through a correctly-named capability); TWEAK 3 (`report-pr-status` rejects `ado:pr:status`, "sharpest single finding of the exercise"); Delights bullet 1 (`goobers explain --human` is the *only* place any of the five `ado:*` strings appear at all — zero hits across `docs/guides`, `config-examples/`, `reference-workflows/`, `examples/`); Docs notes item 3 ("Any documentation of the five `ado:*` capabilities — they are discoverable only via `goobers explain`").

## Proposed direction

Directive, in three parts, all scoped to `internal/capability` + `internal/providerstage`/`v_current`/`v_next`. None of this is gated on the DSL 1.4→2.0 migration (epic #2695) — it is a capability-contract bugfix, not a new DSL feature.

**1. Add `provider:issues:write` and `provider:issues:read`, and retarget every provider-dispatched backlog/issue built-in to require them instead of the GitHub-spelled names.** This is the direct extension of ADR 0002's own precedent (`provider:pr:write` for `open-pr`/`ci-poll`): these built-ins already select their implementation from the configured provider (TWEAK 1 proves the ADO credential path works once the GitHub-spelled string is declared), so per the ADR's first bullet they belong under `provider:<resource>:<verb>`, not a specific provider's name. Update every `internal/providerstage/manifest.go` entry listed in Evidence, plus the matching `policy_actions.go` contracts in both `v_current` and `v_next`, and ship a `goobers fix` migration rule (the same mechanism that already round-trips `dslVersion` pins) to bulk-rewrite `github:issues:write`/`github:issues:read` → `provider:issues:write`/`provider:issues:read` across `reference-workflows/`, `config-examples/`, and `examples/` in the same PR — this is a compiler-enforced rename with zero silent aliasing, exactly ADR 0002's stated migration contract, so every existing GitHub-only workflow needs the mechanical edit too.

**2. Backport `report-pr-status`'s capability contract fix from `v_next` to `v_current`.** #772's design intent (`ado:pr:status` is a genuinely separate, narrower authority than `ado:pr:write` on ADO, with no equivalent split on GitHub) is already accepted and implemented in `v_next` — but 2.0 is preview-only and no load-bearing workflow runs it, so every ADO user on 1.4 hits the bug today with no workaround. Before landing the backport, verify what a GitHub/Gitea-provider gaggle needs to declare under the `v_next` contract as it stands — `policy_actions.go`'s `requiredCapabilities: []capability.Capability{capability.ADOPRStatus}}` names only `ADOPRStatus`, with no accompanying GitHub-side requirement, which needs confirming (not assuming) it still resolves correctly for non-ADO dispatch before that exact contract is copied into 1.4. This is the one capability in this proposal that ADR 0002 explicitly keeps provider-specific, so the fix is "make the manifest's required set match the configured provider," not a new neutral name.

**3. Deprecate, don't delete, the three dead values (`ado:code:read`, `ado:pr:comment`, `ado:work-items:write`).** `internal/capability` has no existing deprecation lifecycle (unlike the DSL feature registry's Preview/GA/Deprecated/Removed in `v_current/types.go`), and inventing one is out of scope here. Minimal safe step: mark the three doc comments deprecated with a pointer to the correct replacement (`provider:issues:write` for the work-items case; no replacement exists yet for the other two, so name them as speculative/never-implemented), and add a non-blocking `validate` warning when a workflow declares one — matching "config as truth": an already-inert grant must keep validating clean, not flip to a hard error. Actual removal from the enum is a separate follow-on once/if a real capability-deprecation mechanism exists.

**Smart-defaults analysis:** a GitHub-only author writing a fresh workflow today declares `github:issues:write` because every example does; after part 1 that same author must declare `provider:issues:write` instead — a real, unavoidable one-line-per-stage edit for every existing config, mitigated by the `goobers fix` rule doing it mechanically. An ADO author gets the entire benefit: the capability that appears in `goobers explain` and validates is now the one their stage actually needs, with no separate ADO vocabulary to discover.

## Alternatives considered

- **Make the five `ado:*` values aliases of their GitHub-spelled counterparts instead of introducing `provider:*` names.** ADR 0002 explicitly rejects this: "the names are not aliases... requiring every provider-specific capability... grows the declaration for every new provider," and dual-grants ambiguous credential admission.
- **Leave the GitHub-spelled requirement in place and just document that it silently routes to ADO.** Cheaper, but perpetuates exactly the naming-lies-about-abstraction-boundary problem ADR 0002's Consequences section calls out ("describing a provider-specific implementation as provider-neutral is a contract bug") — here it's the inverse defect, a provider-neutral operation wearing a provider-specific name.
- **Delete the three dead `ado:*` values outright now.** Turns an inert-but-harmless declaration into a hard validation error for anyone who already has it in a config (confirmed to validate clean today), a bigger and separate discussion than this fix.

## Size and risk

**Part 1 (`provider:issues:write`/`provider:issues:read` + retarget manifests/policy actions + `goobers fix` migration rule): M, wide but mechanical blast radius.** Touches `internal/capability`, both DSL interpreters' manifest/policy-action tables, and every shipped/reference/example workflow's YAML (all currently declare the GitHub-spelled name). The `goobers fix` rule makes the workflow-file edits a single mechanical PR rather than N hand edits; risk is scoped to that migration being complete (a missed shipped workflow fails validation loudly, per ADR 0002's fail-closed contract — not a silent break).

**Part 2 (`report-pr-status` backport): S, narrow.** One manifest entry in `internal/providerstage/manifest.go`, gated on confirming the GitHub/Gitea-side requirement first (see Proposed direction). No workflow migration needed beyond the one `report-status` task already exercised in the coldstart ledger.

**Part 3 (deprecate three dead values): S, no migration.** Doc-comment and `validate`-warning only; zero behavior change for any existing config.

No cross-provider regression risk: GitHub/Gitea-only instances are unaffected by parts 2 and 3, and part 1's `goobers fix` migration keeps them at zero net config change beyond the mechanical rename.
