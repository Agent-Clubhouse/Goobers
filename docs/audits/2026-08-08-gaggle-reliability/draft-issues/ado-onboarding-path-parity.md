# ADO onboarding path: `connect` refuses instead of connecting, no example gaggle, no PAT scope table, `report-pr-status` is undocumented, and `backlog.project` is unchecked

Suggested labels: `area:providers`, `documentation`, `type:feature`, `goobers:needs-human`

## Problem

Every onboarding surface a new user is told to use — `goobers init`, `goobers connect`, `docs/guides/arbitrary-repo-onboarding.md`, `quickstart.md`, `--seed` — assumes GitHub end to end. An operator standing up an Azure DevOps-backed instance has no guided path at all: `init` scaffolds a GitHub placeholder, `connect` refuses ADO identities outright (a recent local fix made that refusal safe rather than silently corrupting the config — see Evidence — but the destination it still can't reach is "connected," not just "refused safely"), there is no ADO example anywhere in the repository to copy from, the production onboarding guide's token table has no ADO row, the single most ADO-native stage in the product (`report-pr-status`) is undocumented outside its own man page, `--seed` has no ADO equivalent for Azure Boards tags, and the one ADO-specific config field (`backlog.project`) is validated by nothing — a typo'd project name passes `--strict --check-repos` clean and fails silently at the first backlog query. The provider engine underneath is genuinely provider-neutral (per the coldstart exercise's own verdict); the on-ramp built on top of it is not.

## Evidence

- **`goobers connect` refuses ADO safely (already fixed, this branch) but still cannot connect it.** `cmd/goobers/connect.go:53-66` (`CONNECT001`/`CONNECT002`/`CONNECT003` diagnostic codes) and `connectADORefusal` (`connect.go:258-289`) print the exact `instance.yaml` block to hand-write, name the four ADO auth kinds, and point at `docs/guides/ado-authentication.md` and `reference-workflows/instance.yaml.example` — replacing the pre-fix behavior (coldstart TWEAK 7, below) that silently wrote a broken hybrid `provider: github` config pointing at an ADO org. `connect.go:281`: `` `--seed` is GitHub-only, so seed Azure Boards tags by hand. `` — the gap is admitted in the refusal text itself. `connect.go:1024,1054`: the rewrite paths that actually touch disk are hardcoded `Provider: providers.ProviderGitHub`.
- **`goobers init` scaffolds a GitHub-only placeholder.** `internal/instance/scaffold.go:210-223` (`defaultConfig`): `Provider: "github"`, `Owner: "your-org"`, `Name: "your-repo"`, `Token: TokenRef{Env: "GOOBERS_GITHUB_TOKEN"}` — no provider-neutral or ADO scaffold path exists.
- **Zero ADO examples anywhere in the repository.** `grep -rl "provider: *ado" --include="*.yaml" .` across `config-examples/`, `reference-workflows/`, `examples/` returns nothing (verified 2026-08-08). `reference-workflows/instance.yaml.example` — the exact file `connectADORefusal` points a stuck ADO user at — is itself GitHub-only (`repos: [{provider: github, ...}]`, lines 10-18); `grep -n "ado\|Azure"` on it returns zero matches.
- **The production onboarding guide has zero ADO content.** `docs/guides/arbitrary-repo-onboarding.md` (535 lines, titled "Onboard an arbitrary repository (tiers 1-2)") — `grep -n "ado-authentication\|Azure DevOps\|ADO\b"` returns nothing. Its §2 "Create least-privilege tokens" (line 58) is a GitHub fine-grained-PAT table only, with no ADO PAT scope equivalent, despite `docs/guides/ado-authentication.md` (137 lines: local/unattended auth, PAT compatibility, Boards work-item mapping, git-transport quota) existing as a genuinely good, ADO-first document that this guide never links.
- **`report-pr-status` is documented nowhere but its own man page.** `grep -rl "report-pr-status" docs/guides/ docs/design/` returns nothing. It appears only in `cmd/goobers/clisynopsis.go:74` and the generated man page — the single stage the coldstart exercise calls "ADO's best feature," invisible to anyone reading the guides.
- **`backlog.project` is validated by nothing.** `api/v1alpha1/common.go:105-107` — `BacklogRef.Project string` — comment: "GitHub repo `owner/name` or Azure DevOps project that scopes the backlog," free text, no format check. `api/validate/validate.go`'s nearest functions, `checkGaggleConnections` (lines 1510-1534) and `checkGaggleAdditionalRepos`/`repoIdentity` (lines 1541-1568), validate `connectionRef` existence and `RepoRef.Project` (the *project* gaggle's repo identity) respectively — neither touches `BacklogRef.Project`. Confirmed today: `project: freemasoninc/TotallyBogus` on a live ADO backlog ref passes `goobers validate --strict --check-repos` with exit 0, while the sibling `repos[]` cross-check for the same instance correctly renders a did-you-mean.
- `docs/audits/2026-08-08-gaggle-reliability/coldstart/coldstart-ado.md`:
  - TWEAK 6 — `init` hardcodes `provider: github`/`your-org`/`your-repo` in both `instance.yaml` and the scaffolded gaggle; post-init validation emits 4 warnings out of the box; `goobers schema instance` and `goobers explain instance.repos` both return `unknown` errors — the file carrying ADO org/project/auth-kind identity has no schema or explain surface at all.
  - TWEAK 7 — pre-fix `connect` behavior: a 3-part ADO identity was refused with a GitHub-only error message; a 2-part guess was silently accepted and wrote a permanently broken `provider: github` config pointing at the ADO org, which then failed reachability against `github.com`. (This branch's `CONNECT001` code, above, is the direct fix for this exact finding.)
  - TWEAK 5 / Delights — no ADO equivalent of `--seed`'s label-derivation exists; the operator had to hand-query the ADO backlog via WIQL to discover the candidate pool was provably empty (zero of 5 work items carried the expected tag).
  - Docs notes — "(1) a single ADO example... zero YAML files... use `provider: ado`"; "(2) An ADO onboarding path... `arbitrary-repo-onboarding.md`... mentions ADO exactly zero times"; "(4) Any mention of `goobers report-pr-status`... It appears in no guide, no example, no reference workflow."
  - Validation gap note — `backlog.project` is "the single most ADO-ambiguous field in the config" and "the one field `validate` has no opinion about."

## Proposed direction

Directive. Sequence as five deliverables under one theme; the first is the substantial one, the rest are independently shippable and much smaller.

**1. `goobers connect` gains real ADO support (the centerpiece).** `connect`'s own refusal message already proves the shape of the target config — it prints the exact block. Extend `connect` to accept the 3-part ADO identity (`org/project/repo` or a `dev.azure.com` URL — the identity `CONNECT001` already parses to build its refusal message, `connect.go:263` `connectADORepo`) and write it, mirroring the GitHub path: rewrite `instance.yaml` `repos[]` with `provider: ado` + the four ADO auth-kind options, rewrite each gaggle's `spec.project` and `spec.backlog.project`, and run the same pre-write reachability preflight `connect` already does for GitHub (an authenticated ADO check, exactly like `--check-repos` already performs — coldstart TWEAK item confirms this check exists and works). This retires `CONNECT001` for the org/project/repo case entirely; keep `CONNECT002`/`CONNECT003` (foreign-provider rewrite guard, unreachable-preflight) as-is since both apply equally to ADO once it is a supported destination.

**2. An ADO example gaggle, checked in where the refusal already points.** Add a `provider: ado` block to `reference-workflows/instance.yaml.example` (the exact file `connectADORefusal` cites) and one full example gaggle (project + backlog + a minimal workflow pair) under `config-examples/gaggles/`, built from the coldstart exercise's own working 7-tweak-clean config as a starting point. Zero-config path is unaffected — this is an additive file, not a change to the GitHub scaffold.

**3. `docs/guides/arbitrary-repo-onboarding.md` gets an ADO branch, not a rewrite.** At minimum: §2's token section links `docs/guides/ado-authentication.md` and states the ADO PAT scopes needed (the existing guide already has this content; the gap is discoverability, not missing material) with a scope table matching `docs/guides/github-token-scopes.md`'s format (precedent: #290/#2677 already established and corrected that table's shape for GitHub). §5 ("Bootstrap the label taxonomy," the `--seed` step) gets an explicit "ADO: seed Boards tags by hand" callout with the WIQL query pattern the coldstart run had to reverse-engineer, until item 1's `--seed` extension (below) exists.

**4. Document `report-pr-status`.** One new subsection in `docs/guides/ado-authentication.md` (it is ADO's flagship stage) plus a mention in the onboarding guide's workflow-authoring pointer (§ "Next: authoring workflows and custom stages") — what it publishes, what a branch policy needs to gate on it, and its capability requirement (coordinate with the companion capability-vocabulary proposal in this batch, since that requirement is currently wrong for ADO).

**5. Validate `backlog.project`.** Add a `checkGaggleBacklogProject` validator alongside the existing `checkGaggleConnections`/`checkGaggleAdditionalRepos` family in `api/validate/validate.go`: for a GitHub backlog, cross-check `Project` against `repos[]` the same way the existing gaggle-to-instance check already does (same did-you-mean UX); for ADO, at minimum confirm non-empty and warn (not fail — no live check without `--check-repos`) if it doesn't match any configured ADO `repos[]` project. Smaller, independent of items 1-4; ships as its own PR.

**Smart-defaults analysis:** none of this changes GitHub zero-config behavior. `init`'s GitHub scaffold, `connect`'s GitHub rewrite, and the existing guide content are untouched — item 1 adds a second `connect` destination selected by the identity shape the user passes, item 2 adds files nobody is forced to read, items 3-4 add sections to existing docs, item 5 adds a warning only reachable by someone who has already configured an ADO backlog. Progressive disclosure: an ADO operator who reads only the connect refusal today gets a correct hand-written config (already true); after item 1 they get the same result without hand-editing YAML.

## Alternatives considered

- **Docs-and-validation only; leave `connect` ADO-refusing permanently.** Cheaper, and item 1 is genuinely the largest piece here. Rejected as the primary recommendation because the refusal message's own guidance proves the shape of the fix is already known — the remaining work is largely plumbing connect already has for GitHub (rewrite + preflight), not new design. If sequencing forces a smaller first cut, land items 2-5 first and treat item 1 as a follow-on — but the direction should still name full support as the target, not settle for a permanently better error message.
- **A `goobers connect --ado` flag instead of identity-shape detection.** Rejected: `CONNECT001`'s refusal already detects the ADO identity shape from the positional argument alone (org/project/repo or a `dev.azure.com` URL); a separate flag duplicates that detection and adds a mode an author has to know exists.
- **Fold `--seed`'s Boards-tag equivalent into item 1 rather than leaving it manual.** Desirable but sequenced out: `--seed`'s GitHub path derives labels from existing GitHub label-creation semantics that have no ADO analog (Boards tags are a different object with different creation/list APIs) — worth its own scoping pass rather than blocking connect's core rewrite on it. The onboarding guide callout in item 3 is the interim mitigation.

## Size and risk

**Item 1 (`connect` ADO support): L.** Real new code path in `cmd/goobers/connect.go` (identity parsing already exists via `CONNECT001`'s detection; net-new is the write + preflight + gaggle rewrite for the ADO shape) plus test coverage matching the existing GitHub `connect` test suite. No migration — additive destination, existing GitHub behavior byte-identical. Recommend filing as its own issue at submission time so it can be sequenced independently of items 2-5.

**Items 2-4 (example gaggle, guide sections, `report-pr-status` docs): S each.** Additive files/sections, zero code change, zero risk to existing behavior. Can land in one PR or three; no dependency ordering between them.

**Item 5 (`backlog.project` validation): S/M.** New validator function following the exact pattern of `checkGaggleConnections`; the GitHub-side did-you-mean check is close to mechanical (reuses the `repos[]` cross-check already built), the ADO-side check needs a decision on whether to require exact match or only non-empty (recommend starting with non-empty + warn, matching `--check-repos`'s existing warn-not-fail posture for live-state checks, and only reaching for a hard did-you-mean error once ADO's org/project inheritance semantics — noted as unresolved in the coldstart ledger — are settled).
