# Agentic GitHub mutations bypass `provider_mutations` — telemetry cannot see what an agent actually wrote

Suggested labels: `area:telemetry`, `area:harness`, `type:bug`, `sprint:v1-breadth`

## Problem

`provider_mutations` records every issue/PR write a *deterministic* Goobers stage makes (`backlog-query`, `issue-close-out`, `open-pr`, and friends all construct their provider client through the same recorder). It records nothing an *agentic* stage's own tool calls write. When an agent files, comments on, labels, or closes an issue directly — which is exactly what a nomination-flow triage/file goober does, and exactly what any agentic stage with issue-write capability can do — that mutation is externally real (the issue exists, the comment posted) but internally invisible: no row, no run attribution, no audit trail.

The consequence is not hypothetical. A single upstream-sync run that filed 55 real GitHub issues left `provider_mutations` showing 2 rows total for that run, both `branch`-kind (the one per-run git-branch marker every run gets regardless of what it does). The most consequential external effect the nomination flows have — creating up to dozens of issues per run — is the one category of write the telemetry system cannot account for at all: not "what did this run do," but "we don't know what this run did, only that it finished."

## Evidence

- `docs/audits/2026-08-08-gaggle-reliability/domains/audit-nomination-flows.md:64-67` (`agentic-mutations-invisible-to-provider-telemetry`, confirmed): `SELECT provider,kind,operation,COUNT(*) FROM provider_mutations WHERE run_id='b703e2bd5db1af70948c60ee074ca16a' GROUP BY 1,2,3` → `github|branch||1`, `github|branch|delete|1` only, against a journal `seq 76` output of `total_filed:55`. The global `GROUP BY kind` on the same table shows `issue|claim 16656`, `issue|label 678`, etc. — real volume, entirely from deterministic-stage paths.
- `internal/runner/run.go:190-200` — the only `ref.touched` event any production path emits unconditionally is the per-run branch marker; it is unrelated to which issue/PR a run actually mutated.
- `internal/harness/copilot.go:60-76` — this instance's harness (Copilot CLI; confirmed the only harness in production per `docs/audits/2026-08-08-gaggle-reliability/domains/audit-code-audit.md:72`) exposes issue/PR mutation as **built-in MCP tools** (`github-mcp-server-issue_write`, `github-mcp-server-add_issue_comment`, `github-mcp-server-sub_issue_write`, etc.) that Copilot itself registers — these are not spawned or wired by Goobers the way the `goobers-io` MCP server is (`internal/harness/copilot_mcp_io.go`), so a capture point aimed only at `gh` CLI shell-outs would miss the dominant real-world channel: an agent filing an issue via its harness's own built-in tool never runs a `gh` subprocess at all.
- `internal/harness/copilot.go:174-177` — the subprocess env the harness constructs for Copilot is a default-deny allowlist (`procenv`), the same mechanism that already injects `GH_TOKEN`/`COPILOT_GITHUB_TOKEN` per capability (`copilot_test.go:171-210`) — i.e., the harness already fully owns and controls the one environment surface every GitHub-writing channel (bare `gh`, `curl`, the built-in `github-mcp-server`) shares before making an HTTPS call.

## Proposed direction

Capture at the harness-owned environment boundary, not at any specific tool. Every channel an agent could use to mutate GitHub — the built-in `github-mcp-server` MCP tools, a shelled-out `gh`/`curl` call, anything else — converges on one HTTPS call to the provider API using the one token the harness already injected. Add a local, per-run logging HTTPS forward proxy that the runner starts alongside the stage (same lifecycle as the worktree/workspace it already manages) and inject its address into the stage's `HTTPS_PROXY` (and the CA it presents into whatever cert-trust variable each tool respects) through the *existing* env-injection pipeline — the same allowlist mechanism that already delivers `GH_TOKEN`. The proxy logs method, path, and status for every mutating (non-GET) request to the configured provider host, tags each with the run id already available in the injecting process, and writes a compact per-run log the rollup ingest maps into `provider_mutations` using the same method/path→kind/operation taxonomy the deterministic path already has (`issue.../comments` → `issue|comment`, `PATCH issues/N` with a `state` body → `issue|close`, etc.) — additive rows in the existing table and schema, not a new mechanism for the rollup side to learn.

Zero-config default: this is harness-level plumbing, not a workflow-authored feature — every agentic stage with any GitHub-write capability gets an audit trail with no YAML change, the same way `GH_TOKEN` injection needs no per-workflow opt-in today.

Scope this to the Copilot adapter first, since it is the only harness in production for this instance; the Claude adapter (`internal/harness/claude.go`) registers no MCP server today and needs the analogous investigation before the same proxy-injection approach can be assumed to cover it.

## Alternatives considered

- **Post-hoc reconciliation** (diff GitHub issue/PR state before and after a run, infer mutations from the delta) — rejected: costs a full extra read pass per run on a GitHub identity already quota-starved (see the audit's cross-cutting rate-limit theme), cannot attribute a specific mutation to a specific stage within a multi-stage run, and is lossy for anything that doesn't survive to the final state (a comment posted then edited, a label added then removed within the same run).
- **Trust the agent's own self-reported summary of what it did** — rejected on direct evidence from this same audit: nomination flows already demonstrate agents recording "no-work" on runs with real, silent, total data loss (`docs/audits/2026-08-08-gaggle-reliability/domains/audit-nomination-flows.md`, quality-sprint's first run). Self-report is exactly the mechanism already shown unreliable; it cannot be the fix for an observability gap the same failure mode created.
- **Require script-stage-only IO: no agentic stage gets a mutating capability directly, only a trusted deterministic executor does** (upstream #1302/TBH-1's typed-proposal-envelope design) — this is the deeper, correct architectural answer, and once implemented per-capability it makes the corresponding proxy-tap redundant for that capability (a migrated write goes through the same `MutationRecorder` deterministic stages already use). It is not a substitute for this proposal today: TBH-1 is `goobers:approved` but unimplemented, scoped as a multi-capability RFC with no committed timeline, and per-capability migration order still to be decided. Recommend both proceed independently — the proxy tap is additive observability deployable now, and each capability's proxy-derived rows become naturally redundant (not wrong, just no longer the only source) as TBH-1 migrates that capability off direct agent credential injection.

## Size and risk

**M.** Blast radius: new per-run proxy process lifecycle in the runner (start/stop paired with stage execution, same pattern as existing per-run worktree/workspace teardown), one new env-injection entry per mutating capability through the existing allowlist mechanism, and a new rollup ingest path parsing proxy logs into `provider_mutations`. No DSL surface change — nothing a workflow author declares differently. Risk is concentrated in correctly plumbing HTTPS interception per harness (cert trust, proxy-env respect) rather than in the rollup/schema side, which reuses an existing table and taxonomy. Needs the Claude-adapter capture point validated separately before claiming full harness coverage — Copilot-only for the first cut is an explicit, stated scope limit, not a silent gap.
